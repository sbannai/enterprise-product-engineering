# EPER API Response Contract

## Scope and compatibility

- Shared API routes retain their existing response shape by default for legacy consumers.
- Clients opt into the version 1 envelope by sending `Accept: application/vnd.eper.v1+json`.
- New integrations should opt into the versioned contract and must not infer application state from free-form error messages.
- This opt-in is a compatibility bridge, not a claim that every API family has migrated. Route-specific behavior must be covered by contract tests before a family is declared standardized.

## Success response

For a response with a body:

```json
{
  "success": true,
  "data": {},
  "meta": { "requestId": "request-correlation-id" }
}
```

The `data` object contains the route's existing successful payload. HTTP status codes remain authoritative. A 204 or 205 response has no body as required by HTTP.

## Error response

```json
{
  "success": false,
  "error": {
    "code": "INVALID_JSON",
    "message": "The request could not be completed.",
    "details": [{ "field": "title", "code": "REQUIRED" }]
  },
  "meta": { "requestId": "request-correlation-id" }
}
```

- `error.code` is a stable uppercase machine-readable identifier; clients should branch on this code and HTTP status, not message text.
- `error.message` is safe for clients and must not expose stack traces, SQL, provider credentials, internal paths, or tenant-private records.
- `details` is optional and limited to validated field/code pairs. Never echo request bodies or secrets.
- A request ID is taken from a valid `x-correlation-id` or generated by the server. The same value is returned in `meta.requestId` and `x-request-id`.

## Error payload bounds

- The server trims error messages and caps them at 500 characters; an empty or non-string message falls back to a generic safe message.
- Error details are optional and limited to the first 50 entries.
- Each detail field name is limited to 128 characters. Missing or malformed detail fields become `unknown`; invalid detail codes become `INVALID_DETAIL`.
- These bounds protect response size and keep malformed internal error metadata from breaking error serialization. They do not replace route-level validation or safe-message review.

## Response headers

Versioned responses include:
- `content-type: application/json; charset=utf-8`
- `cache-control: no-store`
- `x-content-type-options: nosniff`
- `x-request-id: <requestId>`

## Status mapping

| HTTP status | Intended meaning | Example stable code |
| --- | --- | --- |
| 400 | Malformed JSON, invalid input, invalid filters | `INVALID_JSON`, `INVALID_TICKET_INPUT` |
| 401 | Missing or invalid authentication | `UNAUTHORIZED` |
| 403 | Authenticated principal lacks permission or entitlement | `TICKET_ADMIN_PERMISSION_REQUIRED` |
| 404 | Route/resource absent or intentionally non-disclosing | `NOT_FOUND`, `TICKET_NOT_FOUND` |
| 409 | Idempotency key reused with a different payload or state conflict | `IDEMPOTENCY_KEY_CONFLICT` |
| 413 | Request body exceeds configured limit | `REQUEST_BODY_TOO_LARGE` |
| 429 | Rate limit exceeded, where configured | `RATE_LIMITED` |
| 500–599 | Unexpected dependency/storage/service failure | `REQUEST_FAILED`, route-specific safe code |

A route may use a narrower status code when its contract explicitly requires it. Do not return 2xx when a requested mutation failed.

## Security and audit requirements

- Derive tenant, actor, role, and application access from trusted server-side identity; never trust caller-supplied identity headers as authorization.
- Validate request structure and size before persistence or side effects.
- Keep authorization denials and cross-tenant resource responses non-disclosing where appropriate.
- State-changing operations must preserve their durable audit/transaction guarantees; response standardization does not replace audit events.
- Keep legacy compatibility until consumers migrate deliberately. Do not silently change response shape for unversioned clients.

## Required contract tests

For every API family, cover versioned success and errors, invalid JSON and oversized bodies where applicable, authentication/authorization denial, missing resources, conflicts/idempotency, dependency failures, correlation IDs, security headers, and proof that rejected requests do not reach persistence or external side effects. Record current commit and CI run before marking the family PASS.
